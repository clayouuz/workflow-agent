# 游戏架构决策指南

## 定位

本指南用于在编码前讨论并确定游戏项目的整体实现架构。它关注游戏设计如何稳定地落到代码，尤其关注玩家可见表现、生命周期和跨模块协作，不负责创造玩法、拆分实施任务或管理开发进度。

架构不是预先选择一个流行名词，再把项目塞进去。先识别决定架构的真实压力，再组合足够且不过量的结构。

## 核心范式：体验向下，纵切验证

纯自下而上生长容易先形成数据结构和底层系统，最后才发现表现层需要跨模块读取内部状态、拼接零散事件或控制领域对象。纯自上而下也可能产生只适合演示、无法承载规则复杂度的巨型流程控制器。

采用双向收敛：

- 从玩家体验向下定义玩家流程、可见结果、反馈时序和表现契约。
- 在明确边界内实现规则、状态和基础能力。
- 用代表性的端到端纵切验证各层能否组合，而不是先建完所有底层模块。

一条端到端纵切至少说明：

```text
玩家输入 → 输入意图 → 用例/流程编排 → 权威状态变化
         → 状态投影与一次性效果 → 场景/UI/动画/音频反馈
```

## 权威输入与未知项

讨论前先确认以下信息的权威来源：

- 游戏玩法、规则、内容和体验目标：来自用户指定的游戏设计。
- 当前项目结构与行为：来自源码、场景、资源、配置和已安装依赖。
- 引擎或库行为：来自项目实际版本及对应官方资料。
- 平台、性能、联网、确定性、回放、存档、热更新和内容生产约束：来自已确认要求。

设计缺失、含糊或互相矛盾时，保留为待确认问题。不得用惯例、参考游戏或架构偏好替用户补全玩法。

## 架构驱动因素

不要从类或文件开始。先提取会改变模块边界或数据流的因素：

- 核心玩家循环以及循环之间如何切换。
- 主要场景、界面、HUD、弹窗、镜头和反馈通道。
- 规则密度、实体数量、更新频率和性能热点。
- 单局、跨局、账号和静态配置等不同生命周期。
- 动画串并行、延迟反馈、暂停、加速、取消、打断和重入。
- 单机或联网的权威端、预测、回滚和同步要求。
- 随机数、时间、调度、输入和外部服务是否要求可替换或确定性。
- 内容规模、策划配置方式以及最可能发生的变化。
- 现有代码和引擎对象中不可轻易迁移的约束。

每个驱动因素都应能解释某个架构决定；无法对应真实压力的抽象通常不应引入。

## 先处理表现层压力

表现层不是领域层末端的被动适配器。架构讨论必须提前回答玩家看到的结果如何形成。

逐个检查关键体验：

- 什么触发它，玩家立即看到什么，稍后又看到什么？
- 表现依赖哪些权威事实，是否能一次取得完整视图？
- 动画期间再次输入会被拒绝、排队、合并还是打断？
- 暂停、切后台、退出场景、对象销毁或网络重连时如何收束？
- 表现结束是否会反向决定游戏事实？如果会，权威边界是否错误？
- 同一结果有多种表现形式时，规则是否仍保持单一来源？

避免让 UI 或场景监听多个细粒度底层事件后自行推导游戏事实。表现可以决定“怎样展示”，但不应重新计算“游戏发生了什么”。

## 状态分类与所有权

先区分状态的语义，再决定存放位置：

| 状态类型 | 典型内容 | 合理所有者 |
|---|---|---|
| 游戏事实 | 数值、规则结果、胜负、棋盘、实体能力 | 领域或权威模拟模块 |
| 流程状态 | 当前模式、回合阶段、场景迁移、暂停策略 | 应用/流程编排模块 |
| 表现状态 | 当前选择、展开面板、镜头目标、动画阶段 | 表现模块 |
| 引擎对象状态 | 节点、组件、材质、音频实例、资源句柄 | 引擎 View 或基础设施 |
| 持久化表示 | 存档格式、远端 DTO、版本迁移数据 | 基础设施边界 |

对每项关键状态确认：

- 唯一写入者是谁？
- 其他模块通过查询、快照、命令还是事件访问？
- 它能否从更权威的状态重建？
- 生命周期开始和结束由谁控制？
- 是否存在需要手工同步的副本？

缓存和表现快照可以重复数据，但必须能指出权威来源和失效规则。

## 表现契约

领域、流程与表现之间优先形成明确契约，而不是暴露内部对象。

### 输入意图

把点击、拖拽、按键等引擎输入转换为业务意图。意图描述玩家想做什么，不携带节点或组件引用。输入是否允许由权威规则或流程状态判断。

### 状态投影

用于可重复读取、可重建的当前事实，例如棋盘快照、角色状态、当前回合和可执行动作。投影应服务一个明确的表现消费者，避免让 View 拼接多个内部模型。

### 一次性效果

用于不可通过当前状态可靠重放的瞬时反馈，例如受击闪烁、飘字、爆炸、音效和镜头震动。效果需要稳定标识、顺序语义以及重复消费策略；它不是权威事实的替代品。

### 生命周期结果

异步表现应明确完成、取消、超时、被替换和对象销毁时的结果。领域正确性不应依赖动画回调一定到达；确需等待表现的流程应由编排层显式协调。

## 候选架构

至少提出一个满足驱动因素的方案；存在实质取舍时提出两个或三个，不为凑数制造候选。

### 场景中心

状态和行为主要围绕场景节点与组件组织。适合规模小、引擎交互占主导、规则简单且生命周期与场景一致的项目。主要风险是规则散落、场景间复用困难和表现对象成为事实来源。

### 分层或领域中心

将规则与引擎隔离，通过应用层编排。适合规则复杂、需要自动验证、复用或确定性的项目。主要风险是过度抽象，以及忽略表现需求后产生贫弱或碎片化接口。

### Feature Slice

按玩家能力或业务功能纵向组织相关规则、流程和表现代码。适合功能相对独立、团队按功能演进的项目。主要风险是共享规则重复和跨 Feature 协作失控。

### ECS 或数据导向

实体由数据组件组合，系统批量处理。适合大量同构实体、组合能力和性能敏感模拟。主要风险是把 UI、剧情和低数量对象也强行数据化，使控制流难以理解。

### 端口与适配器

把时间、随机数、输入、存储、网络、资源和引擎服务隔离在端口之外。适合存在替换、测试、平台差异或确定性需求的边界。只为真实变化点建立端口，不为每个类创建接口。

### 混合方案

多数实际项目会组合使用：例如按 Feature 组织，在复杂规则内部使用领域模型，在大量战斗实体内部使用 ECS，并通过表现契约连接场景。混合方案必须说明每种范式的适用区域和边界，不能只罗列名称。

## 候选比较

使用同一组问题比较所有候选：

| 维度 | 要回答的问题 |
|---|---|
| 表现适配 | 能否直接支持关键玩家流程、反馈时序和打断语义？ |
| 状态所有权 | 每个事实是否有唯一权威来源，表现能否稳定读取？ |
| 依赖方向 | 高层策略是否被引擎细节反向控制？跨模块协作是否清楚？ |
| 变化成本 | 预期新增内容、规则或表现时，需要改动多少无关模块？ |
| 引擎耦合 | 耦合是否集中在确实需要引擎能力的位置？ |
| 可验证性 | 关键规则和流程能否在合适层级观察和验证？ |
| 性能 | 数据布局、更新频率和对象数量是否匹配真实热点？ |
| 复杂度 | 新增抽象是否解决当前问题，团队是否能持续维护？ |

结论应说明为何选择，而不只给候选打分。某一维度是硬约束时，不用总分掩盖它。

## 模块边界与依赖

模块优先围绕稳定业务能力或变化原因划分，而不是机械地按 `Manager`、`Controller`、`Utils` 分类。

每个模块明确：

- 它拥有的职责和状态。
- 明确不负责的内容。
- 对外提供的意图、查询、投影或事件。
- 允许依赖的模块和禁止反向依赖的边界。
- 创建、启动、暂停、恢复和销毁的责任方。

组合入口负责把具体实现连接起来。业务模块不应自行查找全局单例、场景节点或任意服务定位器。

## 用纵切验证架构

选择最能暴露架构风险的一条体验，不一定是最简单功能。沿途说明：

1. 引擎输入怎样转换为意图。
2. 哪个用例接收意图并协调规则。
3. 谁修改权威状态，失败如何表示。
4. 表现获得哪份状态投影和哪些一次性效果。
5. UI、动画、音频和镜头如何消费。
6. 暂停、取消、重入、切场景或对象销毁时怎样结束。

如果一条纵切需要访问多个模块内部状态、出现双向调用或依赖动画回调维护规则正确性，应回到模块边界重新设计。

## 架构质量复核

最终方案从六方面复核：

1. **职责与位置**：功能和状态是否放在真正拥有它的模块。
2. **模块边界**：是否只通过公共契约协作，没有内部状态访问、跨层调用、循环依赖或无必要的双向依赖。
3. **内聚与耦合**：模块是否服务同一业务目标，修改时是否会牵动无关模块。
4. **单一来源**：规则、状态和计算是否各有唯一权威来源，副本是否可重建且有失效规则。
5. **必要复杂度**：每个抽象是否解决当前问题，没有推测性框架、万能管理器或成比例失衡的接口层。
6. **设计一致性**：实现架构是否满足游戏设计，且没有把技术选择反写成未经确认的玩法约束。

大类、宽接口或重复状态是调查信号，不是脱离上下文的自动失败条件。选择能保护当前架构驱动因素的最小修正。

## 讨论完成条件

架构可以提交用户确认时，应至少具备：

- 架构驱动因素与已确认约束。
- 玩家流程及主要表现压力点。
- 状态所有权和生命周期边界。
- 表现契约及异常路径语义。
- 候选方案的实质取舍和否决理由。
- 最终模块结构、依赖方向、组合入口和引擎边界。
- 一条代表性端到端纵切。
- 风险、演进触发条件和仍需用户决定的问题。

不要为了文档完整而提前设计所有类、接口或未来功能。最终架构应足以约束下一阶段的代码设计，同时允许模块内部实现按实际证据演进。
