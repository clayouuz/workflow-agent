## 修改内容
保留现有开发流程，将最后一句扩展成精简的主动接入规则。目标文本如下：

```markdown
遵守“讨论方案设计 → 确认修改方案 → 讨论代码设计 → 确认代码设计 → 实现”的开发流程，后面环节的开始依赖前面环节的完成。
方案设计阶段不涉及代码。如果任务足够简单、方案已经明确，可直接展示代码设计，经一次确认后开始实现。
代码讨论需要引导用户采用良好的代码设计；代码设计包括具体修改位置、修改内容和必要注释。
如果有会实质影响方案的细节不明确，应提问确认，不自行猜测。

任务台账、测试和工具扩展按 `C:\Users\zhaoyan\workflow-agent\SKILL.md` 执行。
收到用户的任务请求时，主动读取该 Skill 并检查已有任务，不等待用户要求或要求用户先绑定任务：
- 根据任务名称、目标和用户表述进行语义匹配，不使用关键词机械判断。
- 明确命中一个已有任务时，执行 `ledger task bind <id>`，随后执行 `ledger load` 装配该任务上下文，再继续响应用户。
- 多个已有任务都可能命中且无法可靠判断时，列出候选并向用户确认。
- 没有命中已有任务时，才按 Skill 创建并绑定新任务，随后通知用户。
- 不涉及已有任务的一次性普通问答不创建任务台账。
```

## 设计理由
- 全局文件只负责触发条件和任务选择策略；具体 CLI 流程仍由 `SKILL.md` 维护，避免重复和上下文膨胀。
- 先复用已有任务上下文，再考虑创建任务，避免同一事项被拆成重复台账。
- 使用语义判断而不是关键词规则，符合“不过度限制 LLM”的核心原则。
- `bind` 后立即 `load`，确保选择任务和真正装配上下文形成闭环。
- 把提问限制在多个候选都合理的情况，减少用户手动管理台账的负担。
- 顺便统一中文引号和措辞，不改变原有阶段边界。
