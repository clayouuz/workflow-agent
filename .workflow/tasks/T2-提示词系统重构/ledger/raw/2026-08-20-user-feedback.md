# 用户对提示词系统的反馈

- 认可当前提示词系统存在较多冲突。
- 讨论阶段是否记录仍需讨论；担心记录过多增加上下文负担、导致频繁压缩和效果变差。
- `.workflow` 内的修改可以先修改再通知，不满意再删除，如 knowledge；项目实际内容的修改需先批准再执行。“未经批准不得修改任何文件”不是严格约束。
- 不理解历史归档文件随机 ID 的必要性。
- 测试不完善，测试面可能不够广，需要进一步讨论。
- 项目的主要任务是为每次会话提供精确上下文，节省上下文窗口。各文件原计划职责不同，需重新讨论实际重叠。
- 需要评估通过 workflow-agent 加载的上下文不超过 25k 是否可行。
- 需要讨论核心台账模板信息不足的解决方案。
- 增加一个承载讨论结果的通用设计模板，保留 Cocos 特化模板。
- 历史事件格式确定为：`日期: 事件类型 | 内容 | 原因`。
- 启发策略的目的是让 AI 主动提供用户可能缺乏的知识；例如从 Laya 迁移到 Cocos 时，主动提醒两者坐标含义不同。
- 测试流程倾向：先写黑盒测试约定期望结果，再写代码，然后设计白盒测试；无法自动测试时，要让用户自测并给出流程。
- 需要检查测试结果。
- 核心模板只提供通用建议，Cocos 知识放在特化模板。
- 不需要考虑提示词注入。
- knowledge 不需要来源；其主要用于记录美术资源目录、API 文档位置等可复用事实。
- 注释必须有意义，不应为满足形式而添加。
- 项目核心原则：不要给 LLM 过度设限，避免复杂要求降低模型能力并过度占用上下文窗口。
- 挂起的对象可能是某个 benchmark 中的一个 step，不一定是整个任务。
