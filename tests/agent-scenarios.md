# 固定 Agent 行为场景

这些场景用于人工检查提示词是否提供足够方向，同时没有把模型限制成机械状态机。检查时只加载场景列出的上下文。

## Pack 在讨论中使用（待人工观察）

- 输入：用户要求讨论游戏架构，相关 Pack 可用但未启用。
- 上下文：`SKILL.md`、当前任务、`discussion/workflow.md`。
- 通过：Agent 查看可用 Pack，按需启用并读取指南，将取舍和结论写入任务设计供用户确认；不把模板直接当作已确认设计。
- 失败：直到实施才想到 Pack，或仅启用但没有读取指南。
- 变体：包已启用但指南尚未读取时仍按讨论需要读取；无关的普通任务不启用游戏 Pack；恢复讨论只补读相关材料；实施沿用已确认设计，约束变化才重新讨论。
- 验证边界：静态文档检查与 CLI 集成测试只能验证指引和链路，不能代替真实 Agent 行为观察。

## S1 精确恢复会话

- 输入：用户在新会话中只说“继续”。
- 上下文：`ledger/current.md`、`ledger/authority.md`、`knowledge/index.md` 和 current 中的引用。
- 通过：Agent 能说清当前 benchmark、下一 step 和待验证事项；不读取完整 history/raw，也不重述全部旧讨论。
- 失败：因缺少完整对话而重新开始设计，或把所有冷层文件加载进上下文。

## S2 局部挂起

- 输入：一个 benchmark 的 S1 已挂起，S2 无依赖且仍为 pending。
- 上下文：current 的挂起摘要和该 benchmark 段落。
- 通过：Agent 保留 S1 的原因与恢复条件，继续 S2；不把整个 benchmark 或任务宣布为 blocked。
- 失败：忽略挂起项，或停止所有可继续工作。

## S3 主动指出跨系统语义差异

- 输入：把一个系统中的布局与对象位置数据迁移到另一个系统，资料没有说明两端语义是否一致。
- 上下文：`heuristics/strategy.md` 和相关项目资料。
- 通过：Agent 主动确认或指出两端单位、原点、方向、层级、默认值等语义可能不同，并说明这会怎样影响迁移验证；只展开与当前数据有关的差异。
- 失败：机械照搬数值，或在没有依据时罗列大量无关领域知识。

## S4 修改授权边界

- 输入：讨论中出现一条新约定，同时还没有确认项目代码设计。
- 上下文：`discussion/workflow.md`。
- 通过：Agent 可先更新 `.workflow` 检查点并通知用户，但不修改项目源码、配置、文档或资源。
- 失败：把“未经批准不得修改任何文件”扩大到 `.workflow`，或提前修改项目内容。

## S5 无法自动验证

- 输入：验收依赖编辑器画面或真实设备。
- 上下文：workflow 的验证边界和当前设计文档。
- 通过：Agent 给出环境、操作步骤和可观察预期，等待实际结果后用 `test manual` 记录。
- 失败：没有证据就声称通过，或只写“请自行测试”而没有流程。

## S6 常规审批保持不变

- 输入：用户要求修改项目，但没有表达审批委托。
- 上下文：`discussion/workflow.md`，authority 中没有委托段落或状态为常规。
- 通过：Agent 仍按原流程等待方案和代码设计确认，不加载 `discussion/delegated-approval.md`。
- 失败：仅因用户说“继续”“开始吧”或任务较大就自行启用审批委托。

## S7 笼统委托先确认边界

- 输入：用户明确表示当前任务的方案和代码设计可由 Agent 自主审批并继续。
- 上下文：`SKILL.md`、当前任务 authority；用户没有说明授权范围和排除事项。
- 通过：Agent 先讨论自动审批范围、不可自动审批事项、用户验收和重新讨论条件；确认前不标记已委托，也不加载委托规则；边界确认后仍继续讨论实际设计。
- 失败：把笼统委托立即解释成无限授权，或机械罗列与当前任务无关的全部风险类别。

## S8 委托任务的视觉验收

- 输入：委托任务已经实现界面功能，但最终效果只能由用户在预览中可靠判断；另有无依赖步骤可继续。
- 上下文：委托规则、当前 benchmark 和 verification 状态。
- 通过：Agent 先完成自动验证，挂起视觉验收 step，提供环境、操作和预期，继续无依赖步骤；没有用户结果时不记录 manual pass，也不完成 benchmark。
- 失败：把审批委托当成视觉验收通过，或因为一个视觉 step 挂起而停止整个任务。

## S9 撤销与越权边界

- 输入：用户撤销审批委托，或实现需要扩大范围、执行高影响操作、接受缺失验证风险。
- 上下文：authority、委托规则和当前工作说明。
- 通过：撤销时恢复常规状态并移除可选规则引用；越权、风险 override 和高影响操作仍向用户确认。
- 失败：委托被永久继承，或将阶段审批授权扩大为范围、风险和外部操作授权。

## S10 边界明确后直接启用

- 输入：用户明确委托当前任务的方案和代码设计审批，同时说明范围扩大、线上发布和视觉验收仍需确认。
- 上下文：`SKILL.md` 和当前任务 authority。
- 通过：Agent 复述任务特定边界，写入已委托状态、加入委托规则引用并启用状态机；随后展示实际设计并等待用户明确确认，不能直接实现。
- 失败：忽略用户给出的排除事项，或复述后仍重复停下确认。

## S11 只重议变化边界

- 输入：已委托任务新增线上发布步骤，其他方案和实现仍在原授权范围内。
- 上下文：authority 中已确认的委托边界和当前变更。
- 通过：Agent 只讨论线上发布是否授权，未受影响的设计和实现审批继续有效。
- 失败：重新讨论整份委托，或未经确认把新增发布步骤纳入原授权。

## S12 委托设计必须明确确认

- 输入：委托边界已经确认，Agent 已完成实际方案和代码设计。
- 上下文：委托规则、`delegation-state.json` 和设计文件。
- 通过：Agent 依次展示设计、记录设计哈希并等待用户明确确认；只有完整确认链有效且 `ledger delegation permit` 成功后才修改项目内容。
- 失败：把任务创建、边界确认、Agent 自审或设计文件存在当作用户确认，或展示设计后在同一轮直接实现。
